### 1. Storage/Memory/Calldata

这是Solidity 最基础、最常问的。

可以先记一句：

>  Storage = 永久状态
>
>  Memory = 本次执行临时数据
>
>  Calldata = 外部调用传进来的只读参数

#### Storage

Storage 是合约的 持久化存储

~~~solidity
contract Demo {
	uint256 public balance;
	address public owner;
}
~~~

这里 的 balance 和 owner 都会存在 EVM Storage 中。

交易执行结束之后，数据还在。

所以：

~~~solidity
balance = 100;
~~~

本质上是在修改：

~~~
contract storage
~~~

这也是为什么 Storage 贵。

因为它设计区块链的全局状态改变。



<hr>

#### Memory

Memory 是一次函数执行期间的临时内存。

例如：

~~~solidity
function test(uint256 x) external {
	uint256 y = x + 100;
}
~~~

y  这种临时变量通常就在 memory/stack 层面处理。

函数执行完：

~~~
函数开始 -> Memory 创建/使用 -> 函数结束 -> Memory 消失
~~~

所以：

>  Memory 不会跨交易保存。



<hr>

#### Calldata

Calldata 是：

> 外部调用给 Solidity 函数传进来的原始参数数据。

比如：

~~~solidity
function trasfer(address to, uint256 amount) external {
}
~~~

用户调用：

~~~
transfer(0xABC......, 100)
~~~

交易里实际上会带一段：

~~~
calldata
~~~

大致：

~~~
4 bytes function selector
+
32 bytes address
+
32 bytes amount
~~~

所以：

~~~solidity
function foo(uint256 x) external{
}
~~~

这里的 x 可以直接从calldata读取

<hr>

#### 为什么calldata 比 memory 更省？

因为

~~~solidity
function foo(bytes calldata data)
~~~

不需要把参数复制到memory。

而：

~~~solidity
function foo(bytes memory data)
~~~

通常需要复制。

所以对于只读参数： calldata 通常更合适。

这也是以后看 DeFi 合约时 经常看到：

~~~solidity
function swap (
	address[] calldata path
)
~~~

而不是：

~~~solidity
function swap(
	address[] memory path
)
~~~



### 2.Delegatecall

这个非常重要，可以先记：

> Delegatecall = 在“别人家的代码”里执行，但使用“我自己的 Storage”。

这是理解 Proxy 的钥匙。

普通：

~~~solidity
A.call(...)
~~~

相当于： A 去调用B。

B 使用：

~~~
B 的代码
B 的 Storage
B 的 msg.sender
~~~

而：

~~~solidity
A.delegatecall(...)
~~~

是：

> A 借用 B 的代码，但是在A 的上下文里执行。

于是：

~~~
代码： B
Storage： A
address(this) ： A
~~~

这是核心。



举个非常简单的例子：

Implementation：

~~~solidity
contract Logic {
	uint256 public value;
	
	function setValue(uint256 x) external {
		value = x;
	}
}
~~~

Proxy:

~~~solidity
contract Proxy {
	uint256 public value;
	
	function upgradeAndCall(...) external {
		implementation.delegatecall(...);
	}
}
~~~

如果 Proxy：

~~~
delegatecall Logic.setValue(100)
~~~

执行的其实是：

~~~
Logic 的 setValue 代码		-> 

修改 Proxy 的 Storage		->

Proxy.value = 100
~~~

而不是：

~~~
Logic.value = 100
~~~

这就是 Proxy 能成立的原因。

### 3.Proxy

Proxy 本质上解决一个问题：

> 只能合约部署之后，代码怎么升级？

因为传统 Solidity Contract：

~~~
部署	->

Bytecode 固定
~~~

你不能直接修改已经部署的  bytecode

所以出现：

~~~
Proxy 	-> 	(delegatecall) -> 	Implementation
~~~

结构。

<hr>

最经典的结构：

~~~
用户 -> Proxy ->delegatecall -> Implementation
~~~

比如：

~~~
Proxy
	storage:
		balance
		owner
		implementation

Implementation V1
		transfer()
		deposit()
		
Implementation V2
		transfer()
		deposit()
		newFunction()
		
~~~

升级的时候：

~~~
Proxy Storage implementation -> Implementation V1
~~~

改成：

~~~
Proxy Storage implementation -> Implementation V2
~~~

Proxy 不变。用户地址不变。资产也不需要搬。

只是：

> Proxy 开始 delegatecall 新代码

<hr>

### 4.Proxy 最大的坑： Storage Layout

这个需要重点理解！

比如V1:

~~~solidity
contract V1 {
	uint256 public a;
	uint256 public b;
}
~~~

假设：

~~~
slot 0 -> a
slot 1 -> b
~~~

升级成V2:

~~~solidity
contract V2 {
	uint256 public b;
	uint256 public a;
}
~~~

现在：

~~~
slot 0 -> b
slot 1 -> a
~~~

但是 Proxy 里的Storage 没有重新排列。

所以：

~~~
原来 slot 0 = a
现在 V2 认为 slot 0 = b
~~~

那就炸了。

所以Proxy 开发里面有一个非常重要的概念：

> Storage Layout Compatibility

这也是为什么 OpenZeppelin 的 Upgradeable Contract 会特别强调：

~~~
不要随便调整 Storage variable 顺序
不要随便删除变量
不要改变变量类型
~~~

### 5.Event

Event 很多人刚开始学的时候会误认为：

> Event 时给Solidity 合约保存数据的。

不是。

Event 本质是：

> EVM Log

例如：

~~~solidity
event Transfer(
	address indexed from,
	address indexed to,
	uint256 amount
);
~~~

执行：

~~~solidity
emit Transfer(msg.sender, to, amount)
~~~

EVM 会产生：

~~~
Log
~~~

Event 有什么作用？

主要是：

> 给链下系统读取

例如交易所、区块浏览器、The Graph、监听服务。

链上：

~~~
transfer() -> emit Transfer(...) -> EVM Log -> Indexer -> 数据库
~~~

然后前端就能看到：

~~~
Alice -> Bob 100USDT
~~~

### 6.indexed 是什么？

例如：

~~~solidity
event Transfer (
	address indexed from,
	address indexed to,
	uint256 amount
);
~~~

indexed 参数会进入：

~~~
topics
~~~

没有indexed 的：

~~~
amount
~~~

则进入：

~~~
data
~~~

可以简单理解成：

~~~
Event
|---topics
|   |---event signature
|   |---indexed from
|   |---indexed to
|
|---data
|		|---amount
~~~

所以链下程序可以很方便的：

~~~
监听：
from = Alice
~~~

这对你以后做：

> 区块链 Indexer

非常重要。

### 7.Gas

Gas不要简单理解成：

> 执行代码需要的钱

更准确的是：

> Gas是EVM 执行计算/状态操作的资源计量单位。

例如：

~~~
uint256 x = a + b;
~~~

需要Gas。

~~~solidity
SSTORE
~~~

需要更多Gas。

~~~solidity
SLOAD
~~~

也需要Gas。

因为EVM 本质是一个：

> 全球共享的确定性计算机。

如果没有 Gas：

~~~
while(true) {}
~~~

理论上就可以无限占用网络资源。

所以Gas 是一种：

> 计算资源限制 + 防止 DoS 的机制。

### 8.为什么Storage 特别贵？

因为：

~~~
SSTORE
~~~

意味着：

> 修改 Ethereum 全局状态。

例如：

~~~solidity
balance[user] = 100;
~~~

这不是单纯的：

~~~
CPU 算一下
~~~

而是：

~~~
修改全网需要共识维护的 State
~~~

所以：

~~~
计算 -> 便宜 
读Storage -> 更贵
写 Storage -> 通常非常贵
~~~

这也是为什么Solidity 优化经常围绕：

~~~
减少 SLOAD
减少 SSTORE
减少 Storage 变量
减少不必要的 Storage 写入
~~~

展开。

### 9.Transaction Lifecycle

这个建议重点掌握，因为他能把前面所有东西串起来。

一笔 Ethereum 交易：

~~~
用户 -> 钱包签名 -> RPC -> 节点 -> Mempool -> Block -> EVM 执行 -> State Change -> Receipt / Logs
~~~

#### 第一步：用户构造交易

例如：

~~~
to: 0xABC
value: 1 ETH
data: 0x9059cdb...
~~~

其中：

~~~
data
~~~

就是：

> calldata。

### 10.签名

用户钱包使用：

~~~
private key
~~~

对交易签名。

产生：

~~~
signature
~~~

节点可以验证：

~~~
这个交易是不是这个账户发的？
~~~

### 11.RPC

钱包不会直接和矿工/验证者说：

> 帮我执行这个交易。

而是通过：

~~~
RPC
~~~

把交易发给节点。

例如：

~~~
eth_sendRawTranscation
~~~

### 12.Mempool

节点收到之后：

~~~
验证交易 -> Nonce 是否正确？ 余额够不够？Signature 是否正确？ Gas是否合理？ -> 进入Mempool
~~~

之后等待被打包进 Block。

### 13.Block

验证者选择交易：

~~~
Block
|---tx1
|---tx2
|---tx3
|---tx4
~~~

然后执行。

### 14.EVM执行

比如：

~~~solidity
token.transfer(Alice, 100)
~~~

EVM 开始：

~~~
读取calldata -> 解析 function selector -> 找到 trasfer() -> 执行 opcode -> SLOAD -> 计算 -> SSTORE -> emit Event
~~~

于是前面学的东西全部串起来了。

~~~

发生变化。

#### Receipt

可以看到：

~~~

#### Logs

~~~
Transaction
       │

      EVM

 ┌─────┼──────┐
 ▼     ▼      ▼

EVM -> Log -> Kafka / Indexer -> Go 服务 -> 数据库 -> 前端
