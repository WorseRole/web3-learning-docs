### 1. Storage/Memory/Calldata

这是Solidity 最基础、最常问的。

可以先记一句：

>  Storage = 永久状态
>
>  Memory = 本次执行临时数据
>
>  Calldata = 外部调用传进来的只读参数

#### Storage

Storage 是合约的 持久化存储

~~~solidity
contract Demo {
	uint256 public balance;
	address public owner;
}
~~~

这里 的 balance 和 owner 都会存在 EVM Storage 中。

交易执行结束之后，数据还在。

所以：

~~~solidity
balance = 100;
~~~

本质上是在修改：

~~~
contract storage
~~~

这也是为什么 Storage 贵。

因为它设计区块链的全局状态改变。



<hr>

#### Memory

Memory 是一次函数执行期间的临时内存。

例如：

~~~solidity
function test(uint256 x) external {
	uint256 y = x + 100;
}
~~~

y  这种临时变量通常就在 memory/stack 层面处理。

函数执行完：

~~~
函数开始 -> Memory 创建/使用 -> 函数结束 -> Memory 消失
~~~

所以：

>  Memory 不会跨交易保存。



<hr>

#### Calldata

Calldata 是：

> 外部调用给 Solidity 函数传进来的原始参数数据。

比如：

~~~solidity
function trasfer(address to, uint256 amount) external {
}
~~~

用户调用：

~~~
transfer(0xABC......, 100)
~~~

交易里实际上会带一段：

~~~
calldata
~~~

大致：

~~~
4 bytes function selector
+
32 bytes address
+
32 bytes amount
~~~

所以：

~~~solidity
function foo(uint256 x) external{
}
~~~

这里的 x 可以直接从calldata读取

<hr>

#### 为什么calldata 比 memory 更省？

因为

~~~solidity
function foo(bytes calldata data)
~~~

不需要把参数复制到memory。

而：

~~~solidity
function foo(bytes memory data)
~~~

通常需要复制。

所以对于只读参数： calldata 通常更合适。

这也是以后看 DeFi 合约时 经常看到：

~~~solidity
function swap (
	address[] calldata path
)
~~~

而不是：

~~~solidity
function swap(
	address[] memory path
)
~~~



### 2.Delegatecall

这个非常重要，可以先记：

> Delegatecall = 在“别人家的代码”里执行，但使用“我自己的 Storage”。

这是理解 Proxy 的钥匙。

普通：

~~~solidity
A.call(...)
~~~

相当于： A 去调用B。

B 使用：

~~~
B 的代码
B 的 Storage
B 的 msg.sender
~~~

而：

~~~solidity
A.delegatecall(...)
~~~

是：

> A 借用 B 的代码，但是在A 的上下文里执行。

于是：

~~~
代码： B
Storage： A
address(this) ： A
~~~

这是核心。



举个非常简单的例子：

Implementation：

~~~solidity
contract Logic {
	uint256 public value;
	
	function setValue(uint256 x) external {
		value = x;
	}
}
~~~

Proxy:

~~~solidity
contract Proxy {
	uint256 public value;
	
	function upgradeAndCall(...) external {
		implementation.delegatecall(...);
	}
}
~~~

如果 Proxy：

~~~
delegatecall Logic.setValue(100)
~~~

执行的其实是：

~~~
Logic 的 setValue 代码		-> 

修改 Proxy 的 Storage		->

Proxy.value = 100
~~~

而不是：

~~~
Logic.value = 100
~~~

这就是 Proxy 能成立的原因。

### 3.Proxy

Proxy 本质上解决一个问题：

> 只能合约部署之后，代码怎么升级？

因为传统 Solidity Contract：

~~~
部署	->

Bytecode 固定
~~~

你不能直接修改已经部署的  bytecode

所以出现：

~~~
Proxy 	-> 	(delegatecall) -> 	Implementation
~~~

结构。

<hr>

最经典的结构：

~~~
用户 -> Proxy ->delegatecall -> Implementation
~~~

比如：

~~~
Proxy
	storage:
		balance
		owner
		implementation

Implementation V1
		transfer()
		deposit()
		
Implementation V2
		transfer()
		deposit()
		newFunction()
		
~~~

升级的时候：

~~~
Proxy Storage implementation -> Implementation V1
~~~

改成：

~~~
Proxy Storage implementation -> Implementation V2
~~~

Proxy 不变。用户地址不变。资产也不需要搬。

只是：

> Proxy 开始 delegatecall 新代码

<hr>

### 4.Proxy 最大的坑： Storage Layout

这个需要重点理解！

比如V1:

~~~solidity
contract V1 {
	uint256 public a;
	uint256 public b;
}
~~~

假设：

~~~
slot 0 -> a
slot 1 -> b
~~~

升级成V2:

~~~solidity
contract V2 {
	uint256 public b;
	uint256 public a;
}
~~~

现在：

~~~
slot 0 -> b
slot 1 -> a
~~~

但是 Proxy 里的Storage 没有重新排列。

所以：

~~~
原来 slot 0 = a
现在 V2 认为 slot 0 = b
~~~

那就炸了。

所以Proxy 开发里面有一个非常重要的概念：

> Storage Layout Compatibility

这也是为什么 OpenZeppelin 的 Upgradeable Contract 会特别强调：

~~~
不要随便调整 Storage variable 顺序
不要随便删除变量
不要改变变量类型
~~~
