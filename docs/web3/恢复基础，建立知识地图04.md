### 1.建立Foundry的整体地图

现在只需要记住这六个东西：

~~~
                    Foundry
                       │
       ┌───────────────┼────────────────┐
       │               │                │
   forge test      forge script      调试
       │               │                │
       │               │          trace / console
       │               │
       ├───────┬───────┴───────┐
       │       │               │
    Unit    Fork            部署
     Test    Test           Script
       │
       ├───────────────┐
       │               │
     Fuzz          Invariant
       │               │
   随机输入          系统性质
~~~

然后将它和前面的知识链接起来：

~~~
Solidity -> EVM -> DeFi / Protocol -> 安全问题 -> Foundry -> 测试 / 攻击 / 验证 / 调试
~~~

所以Foundry 是最后一层工程工具。

### 2.第一件事： forge test

这是常用的命令

最简单：

~~~bash
forge test
~~~

意思就是：

> 把项目里的测试合约编译，然后执行测试。

比如：

~~~solidity
contract Counter {
	uint256 public number;
	
	function setNumber(uint256 newNumber) external {
		number = newNumber;
	}
	
	function increment() external {
		number--;
	}
}
~~~

写测试：

~~~solidity
contract CounterTest is Test {
	Counter counter;
	
	function setUp() public {
		counter = new Counter();
	}
	
	function test_SetNumber() public {
		counter.setNumber(100);
		
		assertEq(counter.number, 100);
	}
}
~~~

运行：

~~~bash
forge test
~~~

可能得到：

~~~
Ran 1 test for test/Counter.t.sol:CounterTest
[PASS] test_SetNumber()
Suite result: ok. 1 passed; 0 failed
~~~

这里要形成一个非常重要的知识：

> Foundry Test 本质上是在模拟EVM 执行环境，然后验证你的合约状态有没有按照预期变化。

### 3.setUp()是干什么的？

测试里经常看到：

~~~
function setUp() public {
	counter = new Counter();
}
~~~

类似于 Java 单元测试里面的：

~~~Java
@BeforeEach
void setUp() {
	'''
}
~~~

每个测试开始之前都会执行。

比如：

~~~solidity
function setUp() public {
	token = new MockERC20();
	lending = new Lending(token);
}
~~~

然后：

~~~solidity
function test_Deposit() public {
	...
}
function test_Borrow() public {
	...
}
function test_Liquidation() public {
	...
}
~~~

每个测试都会拥有自己的初始化环境。

### 4.Foundry 真正牛的地方：Cheatcodes

这是一定要掌握的：

测试合约通常：

~~~
import {Test} from "forge-std/Test.sol";

contract xxTest is Test{
}
~~~

Test 给提供了一套非常强的测试工具。

例如：

> 下一次合约调用，把msg.sender 假装成 alice。

例如借贷协议：

~~~solidity
vm.prank(alice);
lending.deposit(200, ether);
~~~

那么在Lending合约里面：

~~~solidity
msg.sender
~~~

就是：

~~~
alice
~~~

而不是测试合约。

### 5.这个东西特别重要：prank

比如你有：

~~~solidity
function withdraw(uint256 amount) external {
	require(balance[msg.sender] >= amount);
	
	balance[msg.sender] -= amount;
}
~~~

测试：

~~~solidity
address alice = makeAddr("alice");

function test_withdraw() public {
	vm.prank(alice);
	
	vault.withdraw(100);
}
~~~

实际上是在模拟：

~~~
Alice
  │
  │ withdraw(100)
  ↓
Vault
  │
  └── msg.sender = Alice
~~~

比之前可能用Remix手动切账户方便太多。

### 6.deal(): 直接给账户钱

比如：

~~~solidity
deal(address(token), alice, 1000 erther);
~~~

直接让：

~~~
alice
token balance = 1000
~~~

如果是 ETH：

~~~solidity
deal(alice, 100 ether);
~~~

然后：

~~~solidity
vm.prank(alice);
vault.deposit{value: 10 ether}();
~~~

这对DeFi 测试特别爽。

因为不需要：

~~~
先部署 Token -> mint -> approve -> transfer -> 再测试
~~~

测试环境可以快速构造出来。

### 7.expectRevert

这就是测试异常。

比如：

~~~solidity
function withdraw(uint256 amount) external {
	require(balance[msg.sender] >= amount, "INSUFFICIENT_BALANCE");
	
	...
}
~~~

测试：

~~~solidity
function test_RevertWhen_InsufficientBalance() public {
	vm.expectRevert("INSUFFICIENT_BALANCE");
	
	vault.withdraw(100);
}
~~~

意识：

> 我就是期待这次调用失败。

如果居然成功：

~~~
FAIL
~~~

这对于后面做安全测试非常重要。

例如：

~~~
无权限调用 upgrade
        ↓
应该 revert

普通用户调用 liquidation
        ↓
应该 revert

HF > 1 强行清算
        ↓
应该 revert

nonce 已使用的签名
        ↓
应该 revert
~~~

### 8.然后进入第一个核心：Fork Test

这个对以后DeFi 非常重要。

普通测试：

~~~
你的本地 EVM
  ↓
空白世界
~~~

Fork Test:

~~~
Ethereum Mainnet
        ↓
        Fork
        ↓
       本地 EVM
        ↓
     真实协议状态
~~~

例如：

~~~bash
forge test --fork-url $RPC_URL
~~~

你可以在本地 fork 一个真实Ethereum 网络状态。

然后测试：

~~~
真实 Uniswap
真实 Token
真实 Pool
真实 Oracle
真实余额/状态
~~~

但：

> 你实际执行的交易不会真的改变 Mainnet。

这就是为什么 DeFi 开发非常喜欢 fork test。

### 9.举一个重点理解的场景

假设你研究某个借贷协议。

你想知道：

> 如果 ETH 从 $3000 跌到 $2000, 某个账户会不会被清算？

普通单元测试：

~~~
自己写一个假的 Lending
自己写假的 Token
自己写假的 Oracle
自己写假的 Position
~~~

这只能证明：

> 我得代码逻辑在这个假环境里成立。

Fork Test 可以：

~~~
真实 Ethereum 状态
        ↓
真实 Lending Protocol
        ↓
真实 Token
        ↓
真实 Oracle
        ↓
模拟价格变化
        ↓
测试 liquidation
~~~

这才是真正接近生产环境的测试。

### 10.Fuzz Test

这个需要重点看看。

普通测试：

~~~solidity
function test_Deposit() public {
	deposit(100);
}
~~~

你只测试：

~~~
100
~~~

Fuzz:

~~~solidity
function testFuzee_Deposit(uint256 amount) public {
	...
}
~~~

Foundry 会自动生成大量：

~~~
0
1
2
10
100
99999
type(uint256).max
...
~~~

然后不停测试。

核心思想：

> 我不知道什么输入会出问题，所以让Foundry 帮我找。

### 11.比如你的清算逻辑

看之前做过类似：

~~~
collateral
debt
liquidation threshold
~~~

假设：

~~~solidity
function liquidatable(uint256 collateral, uint256 debt) public pure returns (bool) {
	return collateral * 100 < debt * 150;
}
~~~

你可以：

~~~solidity
function testFuzz_Liquidation(uint256 collateral, uint256 debt) public {
	...
}
~~~

Foundry 会疯狂尝试：

~~~
collateral = 1
debt = 1

collateral = 100
debt = 150

collateral = 0
debt = 100

collateral = type(uint256).max
debt = ...

...
~~~

他特别容易帮你找到：

* 除0
* overflow
* rounding
* 边界条件
* 极端金额
* 极端价格

这就是为什么：

> DeFi + Fuzz 是非常重要的组合。

### 12.Invariant Test

这个和Fuzz有一点像，但思维层级完全不同。

Fuzz 更像：

> 给你各种输入，你看看函数会不会炸。

Invariant：

> 无论用户怎么操作，这个系统永远不能违反某个规则。

比如Token ：

~~~
totalSupply = 所有用户余额之和
~~~

这是一个 invariant。

比如你的交易所：

~~~
总资产 = 用户余额综合 + 系统资产
~~~

或者：

~~~
订单薄买单价格必须有序
~~~

或者永续：

~~~
所有仓位保证金 accounting 必须守恒
~~~

这就非常接近真正的协议工程。

### 13.把Fuzz 和 Invariant 区分清楚

可以这样记：

#### Fuzz：

~~~
一个函数 -> 大量随机输入 -> 找 Bug
~~~

#### Invariant：

~~~
整个系统 -> 随机执行各种操作 -> 检查系统永远满足某个性质
~~~

例如：

~~~
deposit()
withdraw()
borrow()
repay()
liquidate()
transfer()
...
       ↓
不断随机组合
       ↓
Invariant：
totalAssets >= totalDebt
~~~

这个非常适合以后测试自己的：

> 现货 + 永续 + 清算 + 结算系统。

### 14.Script

测试是：

> 我验证代码

Script是：

> 我真的执行部署/交互流程。

例如：

~~~
部署 Token -> 部署Oracle -> 部署 Lending -> 部署 Oracle -> 设置参数 -> 添加资产
~~~

可以写：

~~~solidity
contract DeployScript is Script {
	function run() external{
		vm.startBroadcast();
		
		Token token = new Token();
		Lending lending = new Lending(address(token));
		
		vm.stopBroadcast();
	}
}
~~~

运行：

~~~Bash
forge script script/Deploy.s.sol
~~~

真正部署的时候再制定RPC 和私钥等参数。

### 15.最后就是Debug

面的时候很有价值的一块。

比如测试：

~~~bash

~~~

例如：

~~~

 └── deposit()

      ├── SLOAD
      ├── SSTORE
      ├── CALL
      │    └── transfer()
      └── LOG
~~~

这时候你就能把我们前面学的：

~~~
EVM
│
├── CALL
├── DELEGATECALL
├── SLOAD
├── SSTORE
├── LOG
├── REVERT
└── RETURN
~~~

真正串起来。

> Foundry 不是独立的一章。
