### 1.重入攻击 Reentrancy

这是Solidity 安全 最经典的一个。

核心思想：

> 合约调用外部合约时，对方可以在你的函数还没执行完之前，再反过来调用你的函数。

看一个经典的错误：

~~~solidity
function withdraw() external {
	uint256 amount = balances[msg.sender];
	(bool success, ) = msg.sender.call{value: amount}("");
	require(sucess);
	balances[msg.sender] = 0;
}
~~~

看起来很正常：

~~~
取余额 -> 转 ETH -> 余额清零
~~~

但是：

~~~
msg.sender
~~~

可能是一个恶意合约

它收到ETH后可以：

~~~
fallback() -> 再次调用 withdraw() -> 又读取 balances[msg.sender] -> 还是原来的余额 -> 再次转 ETH -> 再次 withdraw() -> ...
~~~

于是：

~~~
withdraw() -> 攻击合约 -> withdraw -> 攻击合约 -> withdraw -> ...
~~~

这就是：

> Reentrancy

#### 怎么解决？

##### CEI

> Checks -> Effects -> Interactions

也就是：

~~~solidity
function withdraw() external {
	uint256 amount = balances[msg.sender];
	require(amount > 0);
	balances[msg.sender] = 0;
	(bool success, ) = msg.sender.call{value: amount}("");
	require(seccess);
}
~~~

顺序：

~~~
Checks -> 修改状态 -> 外部调用
~~~

而不是：

~~~
外部调用 -> 修改状态
~~~

还可以使用：

~~~solidity
nonReentrant
~~~



### 2.权限控制

这个非常朴素，但现实里非常致命。

例如：

~~~solidity
function setOracle(address oracle) external {
	oracleAddress = oracle;
}
~~~

如果忘了：

~~~solidity
onlyOwner
~~~

那么：

~~~
任何人 -> setOracle(attackerOracle) -> Oracle 被替换 -> 价格完全由攻击者控制 -> 清算/借贷全部失效
~~~

所以权限问题本质是：

> 谁有资格改变协议的关键状态？

#### DeFi 中哪些操作通常需要权限？

比如：

~~~
修改 Oracle
修改手续费
修改清算参数
暂停协议
升级 Implementation
修改管理员
添加资产
设置白名单
铸造 Token
~~~

这些都是：

> 高权限操作。

所以写合约的时候需要问问自己：

~~~
这个函数谁能调用？
任何人？
Owner？
Governance？
Keeper？
Liquidator？
~~~

### 3.精度/舍入

这个特别容易被低估。

因为Solidity：

~~~
没有传统浮点数
~~~

DeFi 通常使用整数 + scale。

例如：

~~~
1 USDC = 1000000
~~~

因为 USDC 6 decimals。

假设：

~~~solidity
uint256 result = amount * price / 1e18;
~~~

这里：

~~~
1 / 3
~~~

结果不会得到：

~~~
0.333333333333...
~~~

而是整数截断:

~~~
0
~~~

#### 还有什么危险？

假设协议计算：

~~~
利息
手续费
兑换数量
抵押率
清算奖励
份额
~~~

如果：

~~~
向下舍入
~~~

或者：

~~~
向上舍入
~~~

方向错了，可能导致：

~~~
用户多拿钱
协议少拿钱
~~~

单词可能只有：

~~~
0.000001 ETH
~~~

但如果：

~~~
100万次交易
~~~

累计起来就很可怕。

#### DeFi一个重要原则

以后看代码时要特别注意：

> 谁应该吃掉 rounding error ？

比如：

~~~
用户兑换
协议兑换
铸造 shares
赎回 shares
借款利息
清算奖励
~~~

通常需要明确：

~~~
用户获利方向？
协议获利方向？
~~~

不能随便：

~~~
a * b / c
~~~

### 4.Oracle 操纵

刚才说了Oracle。

现在从攻击角度看。

假设一个借贷协议：

~~~solidity
ETH Price = price;
~~~

攻击者发现：

~~~
Oracle 使用某个小型 DEX 的现货价格
~~~

池子：

~~~
ETH = 100
USDC = 200000
~~~

攻击者使用闪电贷：

~~~
借 10000000 USDC
~~~

然后疯狂：

~~~
买 ETH
~~~

把池子价格：

~~~
$2000 -> $5000
~~~

如果Oracle 直接读取这个池子的 spot price：

~~~
Oracle:
ETH = $5000
~~~

实际上：

~~~
真实市场：
ETH 约等于 2000
~~~

攻击者于是可以：

~~~
抵押少量 ETH -> 协议认为 ETH 很值钱 -> 借大量USDC -> 把 USDC 拿走 -> 恢复池子价格 -> 闪电贷还钱
~~~

协议留下：

> 坏账。

### 5.闪电贷攻击

闪电贷：

> 在一笔交易内借钱，并且必须在这比交易结束前还回去。

例如：

~~~
Flash Loan -> 借 $100M -> 操纵价格 -> 利用漏洞 -> 获利 -> 还 $100M -> 交易结束
~~~

如果没还：

~~~
整个交易 revert
~~~

所以闪电贷的恐怖之处是：

> 攻击者不需要先拥有 $100M。

#### 但注意

闪电贷 不等于 漏洞。

比如：

~~~
正常协议 + 闪电贷
~~~

没什么问题。

真正危险的是：

~~~
闪电贷 + Oracle 操纵
~~~

或者：

~~~
闪电贷 + AMM 价格依赖
~~~

所以要是被问到：

> 闪电贷攻击是什么？

不要只回答：

> "借很多钱攻击"。

应该回答：

> 闪电贷提供无抵押的瞬时资金，攻击者利用资金在同一交易内操纵价格、状态或逃离路径，从协议逻辑漏洞中获利。

### 6.清算边界

这个跟之前做永续的时候非常相关。

假设：

~~~
Maintenance Margin = 5%
~~~

你写：

~~~solidity
if(marginRatio < 5%) {
	liquidate();
}
~~~

问题来了：

~~~
marginRatio = 5%
~~~

到底清不清？

这是：

> 边界条件。

#### 更危险的是价格变化

假设：

~~~
BTC = $100000
~~~

账户：

~~~
Margin = $10000
Position = $100000
~~~

突然：

~~~
BTC 100000 -> 95000
~~~

如果：

~~~
Mark Price
Oracle Price
Index Price
Last Price
~~~

使用不同价格：

~~~
Liquidation Price
~~~

就可能出现差异。

#### 清算系统需要考虑

~~~
什么时候可以清算？
什么时候不能清算？
清算多少？
清算价格是多少？
清算奖励多少？
清算后剩余保证金多少？
~~~

还有：

~~~
HF = 1
~~~

到底：

~~~
>= 1 安全？
< 1 清算？
~~~

还是：

~~~
<= 1 清算？
~~~

这些都要非常明确。

之前做永续时如果出现：

~~~
if margin < maintenanceMargin
~~~

这种代码，真正需要问的是：

>  这个 <  是不是正确的？

### 7.签名重放 Replay Attack

这个属于Web3 特有的安全问题。

比如用户签名：

~~~
Alice:
“授权 Bob 转 100 USDC”
~~~

攻击者拿到签名之后：

~~~
执行一次
~~~

如果协议没有防重放：

~~~
再次执行
再次执行
再次执行
~~~

用户就可能被重复扣钱。

#### 怎么防？

##### Nonce

~~~
Alice nonce = 10
~~~

签名：

~~~
nonce = 10
~~~

使用一次之后：

~~~
nonce = 11
~~~

旧签名：

~~~
nonce = 10
~~~

再次使用：

~~~
revert
~~~

##### 还有 Chain ID

假设：

~~~
Etherem Mainnet
Chain ID = 1
~~~

用户签名。

如果没有把Chain ID 纳入签名：

~~~
Mainnet 签名
~~~

可能被拿到：

~~~
其他链
~~~

再次使用。

所以现代签名标准通常会把：

~~~
chainId
nonce
contract address
function
parameters
deadline
~~~

等重要信息纳入签名。

### 8.升级风险

接之前提到的Proxy。

结构：

~~~
User -> Proxy -(delegatecall)-> Implementation
~~~

假设：

~~~
Owner
~~~

可以升级：

~~~
UpgradeTo(newImplementation)
~~~

那么：

~~~
Owner 被攻击 -> 攻击者成为 Owner -> upgradeTo(MaliciousContract) -> 所有用户调用 Proxy -> delegatecall 恶意代码 -> Storage / Funds 全部危险
~~~

所以：

> Proxy 最大的风险之一就是升级权限。

### 9.Upgrade 不只是权限问题

还有一个非常重要：

> Storage Layout

V1:

~~~solidity
uint256 balance;
address owner;
~~~

可能：

~~~
slot 0 = balance
slot 1 = owner
~~~

V2 如果乱改：

~~~
address owner;
uint256 balance;
~~~

那么：

~~~
slot 0 = owner
slot 1 = balance
~~~

但是旧Storage 不会自动跟着改变。

结果：

~~~
owner 读成奇怪的数据
balance 读成奇怪的数据
~~~

所以 Upgradeable Contract 要考虑：

~~~
权限 + Storage Layout + Initializer + Upgrade Authorization + Implementation 自身安全
~~~

### 10.把这些攻击串起来理解

假设你写了一个：

> DeFi Lending Protocol

里面有：

~~~
Deposit
Borrow
Repay
Liquidate
Oracle
Proxy
~~~

攻击者可能这样搞：

~~~
攻击者 -> Flash Loan -> $100M USDC -> 操纵 AMM -> Oracle Price 被操纵 -> Lending Protocol -> 错误判断价格 -> 抵押物价值虚高 -> Borrow -> 借出大量资产 -> Oracle恢复 -> 攻击者还 Flash Loan -> 协议产生坏账
~~~

这就是典型的：

> 经济攻击链。

### 11.再看永续合约

永续系统可能是：

~~~
User -> Open Position -> Oracle / Mark Price -> PnL -> Margin Ratio -> Liquidation
~~~

那么攻击面就是：

~~~
Oracle 操纵 -> 错误 Mark Price -> 错误 PnL -> 错误 -> Liquidation Price -> 错误清算
~~~

再加上：

~~~
精度问题
清算边界
资金费率
价格延迟
极端行情
~~~

就构成了一个完整的：

> Perpetual Risk Engine
